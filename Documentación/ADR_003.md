# ADR 003: Separación Analítica mediante el Patrón CQRS

* **Estado:** Aceptado

## Contexto y Declaración del Problema
El sistema debe procesar transacciones transaccionales (OLTP) de alta velocidad (usuarios consultando su itinerario - 800ms) y, al mismo tiempo, el requerimiento UC7 exige que el equipo de datos ejecute consultas analíticas pesadas para monetizar información (OLAP). Mezclar ambas cargas de trabajo en la misma base de datos degradará el rendimiento y pondrá en riesgo QA2.

## Drivers
* QA2: Rendimiento < 800ms para consultas de usuarios en la web.
* UC7: Ejecución de consultas analíticas pesadas.

## Decisión
Se implementará el patrón **CQRS (Command Query Responsibility Segregation)** a nivel arquitectónico. Mantendremos una base de datos principal optimizada para las lecturas/escrituras de la aplicación (Documental o Relacional) y una base de datos analítica separada (ej. ClickHouse, BigQuery o un Data Warehouse) alimentada vía eventos.

## Consecuencias

* **Bien:** Aislamiento total de rendimiento. Las consultas monstruosas del equipo de datos no afectarán el tiempo de carga del itinerario del viajero.
* **Bien:** Los modelos de datos se pueden optimizar para sus respectivos propósitos (esquemas normalizados/documentales para la App, esquema de estrella/columnar para Analítica).
* **Mal:** Datos duplicados, aumentando los costos de almacenamiento.
* **Mal:** La base de datos analítica no tendrá los datos en tiempo real absoluto (consistencia eventual basada en la velocidad de propagación de los eventos).
